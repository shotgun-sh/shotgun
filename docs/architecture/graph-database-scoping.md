# Graph Database Storage and Scoping

This document describes how Shotgun stores, enumerates, and scopes Kuzu graph databases — particularly how concurrent sessions avoid interfering with each other.

## Storage Layout

All graph databases are stored under `~/.shotgun-sh/codebases/`. Each indexed repository gets a single `.kuzu` file named by a deterministic graph ID:

```
~/.shotgun-sh/codebases/
  a1b2c3d4e5f6.kuzu   # /Users/alice/work/project-alpha
  f7e8d9c0b1a2.kuzu   # /Users/alice/work/project-beta
  ...
```

### Graph ID Generation

Graph IDs are generated by `CodebaseGraphManager.generate_graph_id()` in `src/shotgun/codebase/core/manager.py`:

```python
@classmethod
def generate_graph_id(cls, repo_path: str) -> str:
    normalized = str(Path(repo_path).resolve())
    return hashlib.sha256(normalized.encode()).hexdigest()[:12]
```

The path is resolved to an absolute path before hashing, so symlinks and relative paths map to the same graph ID. The 12-character hex prefix gives ~48 bits of entropy — sufficient to avoid collisions across repositories on a single machine.

## Database Enumeration

Three methods in `CodebaseGraphManager` need to enumerate databases:

| Method | Purpose |
|---|---|
| `detect_database_issues()` | Startup health check — opens each DB to verify it's not corrupted or locked |
| `list_graphs()` | Used by `shotgun codebase list` and the graph service to show indexed repos |
| `cleanup_corrupted_databases()` | Removes databases that can't be opened (called during startup and recovery) |

All three use the `_iter_databases()` method as a single entry point for enumeration. This method returns `(graph_id, path)` pairs for databases that should be visible to the current process.

## Concurrent Session Scoping

### The Problem

Kuzu uses exclusive file locks on `.kuzu` database files. When two Shotgun sessions run simultaneously on different repositories, the startup health check (`detect_database_issues()`) would previously glob **all** `.kuzu` files and attempt to open each one. Any database held open by a peer session was reported as "locked," producing a blocking dialog — even though the current repo's database was perfectly fine.

### The Solution: Process-Wide Scope

A class variable `_scope_graph_ids` on `CodebaseGraphManager` controls which databases are visible:

```
_scope_graph_ids: ClassVar[list[str] | None] = None
```

- **`None`** (default) — no restriction, all databases are enumerated (full glob)
- **`[graph_id, ...]`** — only these specific databases are enumerated

At process startup, `main.py` sets the scope to the current working directory's graph ID:

```python
CodebaseGraphManager._scope_graph_ids = [
    CodebaseGraphManager.generate_graph_id(os.getcwd())
]
```

Because `_scope_graph_ids` is a `ClassVar`, every instance of `CodebaseGraphManager` created anywhere in the process — TUI, `shotgun run`, `shotgun codebase index` — automatically respects the scope with zero parameter passing.

### The Exception: `shotgun codebase list`

The `list_codebases` CLI command legitimately needs to show all indexed repositories. It clears the scope before querying:

```python
CodebaseGraphManager._scope_graph_ids = None
```

This is the only place the scope is intentionally unset.

### How `_iter_databases()` Works

```python
def _iter_databases(self) -> list[tuple[str, Path]]:
    if self._scope_graph_ids is not None:
        return [
            (gid, self.storage_dir / f"{gid}.kuzu")
            for gid in self._scope_graph_ids
            if (self.storage_dir / f"{gid}.kuzu").exists()
        ]
    return [(p.stem, p) for p in self.storage_dir.glob("*.kuzu")]
```

When scoped, it constructs paths directly from the known graph IDs instead of globbing — the peer session's databases are never touched.

## Key Files

| File | Role |
|---|---|
| `src/shotgun/codebase/core/manager.py` | `CodebaseGraphManager` — storage, enumeration, scoping logic |
| `src/shotgun/main.py` | Sets `_scope_graph_ids` at process startup |
| `src/shotgun/cli/codebase/commands.py` | Clears scope in `list_codebases()` |

## Future Considerations: Multi-Repo Support

Users have requested the ability to index multiple repositories and have all of them available within a single Shotgun session — e.g., querying across a frontend repo and its backend counterpart simultaneously.

This is a natural extension of the scoping mechanism: `_scope_graph_ids` already accepts a list, so the enumeration layer could support multiple repos without changes. However, the work to actually deliver multi-repo support is significantly broader:

- **UX design** — How does a user select which repos to include? How are cross-repo results presented? How does the session indicate which repo a result came from?
- **UI changes** — The current TUI assumes a single-repo context throughout. Multi-repo would touch the chat interface, file viewers, and agent prompts.
- **Agent behavior** — Agents would need to understand repository boundaries when reading files, suggesting changes, and building context.
- **Indexing workflow** — Today, indexing is tied to the CWD. Multi-repo needs a way to manage a set of indexed repos and keep them in sync.

The scope and UX of this feature are still undefined. This section exists to document the request and note that the scoping infrastructure was designed with this possibility in mind, even though it currently only scopes to a single repo.
